== Constat central — la formulation du BACKLOG était inexacte

L'audit S-012 (faits vérifiés, jamais supposés) révèle **deux erreurs** dans
la définition d'ACADEMY-4, corrigées avant d'écrire une ligne de code :

. *`MaterialUpdateContract` est une data class, pas une interface.* Le BACKLOG
   disait « implémenter l'interface MaterialUpdateContract ». Le JAR N0
   (`runtime-contracts:0.0.1`, inspecté) expose : `MaterialUpdateContract`
   (**data class** : `remoteUrl`, `currentVersion`, `latestVersion`),
   `MaterialUpdateResolver` (**interface** : `fetchLatest`, `pull`),
   `MaterialUpdateResult` (sealed). Erreur de type **et** de propriétaire.
. *Le transport appartient au bureau, pas à academy.* La vision § 3.2 tranche :
   « Bureau **synce** le matériel (transport git → office/). Academy **consomme**
   pédagogiquement. Un seul propriétaire par verbe. **bureau l'implémente,
   academy le lit**. » Implémenter git dans academy dupliquerait `BUREAU-3` et
   contredirait la doctrine.
. *Le transport du bureau n'existe PAS encore.* `grep` S-012 : `bureau-gradle`
   ne contient que `BureauPlugin`/`BureauExtension`/`BureauPluginTest` ;
   `pullMaterial` n'apparaît que dans la **KDoc** de `BureauPlugin.kt:13` —
   **zéro** `tasks.register` dans le borough. Le guide academy documente donc
   le **mécanisme figé** (git pull de la version taguée), **jamais** une
   commande `pullMaterial` exécutable inexistante (leçon S-007 `moodle:4.5` et
   S-011 « vérifier la source avant de citer un précédent »).

== Dogfooding (preuve réelle — leçon S-007/S-009/S-011)

`publishToMavenLocal` + consommateur transitoire `/tmp` (pattern Règle 2), avec
des **pivots EPIC K réels** écrits comme un producteur les écrit :

. matériel complet (SPG + SLIDES @ v1.0) → **READY**
   (`[academy] training material satisfies the requirement - present: SPG, SLIDES`).
. version requise v2.0, matériel v1.0 → **FAIL** actionnable
   (`outdated (expected version v2.0)`).
. type QUIZ attendu absent → **FAIL** actionnable (`missing QUIZ`).
. aucune exigence déclarée, aucun matériel → **SUCCESS** `nothing to verify`
   (backward compat).
. installeur Linux généré → `MATERIAL.md` présent, `sh -n` **VALIDE**, et
   `grep pullMaterial` = **0** (aucune commande inexistante citée).

**Découverte du dogfooding** : le cas 4 avec `materialExpectedTypes` renseigné
**sans** `materialRemoteUrl` était traité comme « pas d'exigence » — donc
silencieusement ignoré. Correctif TDD : `hasRequirement()` considère désormais
aussi les types attendus (nommer les artefacts voulus **est** une exigence).
Preuve que le dogfooding trouve ce que le test vert ne voyait pas.
