== Contexte

Depuis le recadrage pilote S-002 (D-ACADEMY-1..4), le borough Bagdad livre
une **machine d'expérimentation complète** du pipeline cccp.education via
un **installeur hybride multiplateforme** :

```
┌─────────────────────────────  HOST  ─────────────────────────────┐
│  Docker        (socle conteneurs)                                │
│  Java Temurin 25 + Gradle 9.7.1  →  lance les plugins            │
│      education.cccp (bakery, document, slider, capsule, ...)     │
└──────────────────────────────┬───────────────────────────────────┘
                               │ docker compose
┌───────────────────────────── ▼  DOCKER  ─────────────────────────┐
│  Moodle 4.x  (LMS formation, cours seedé)                        │
│  PostgreSQL  (base Moodle, volumes persistants)  ← pilote 09-22  │
│  Ollama      (runtime LLM, modèles, port 11434)                  │
│  Portainer   (GUI Docker, port 9000 — remplace Docker Desktop)   │
│  workspace   (session zsh + opencode via conteneur)              │
└──────────────────────────────────────────────────────────────────┘
```

La ressource est **mono-utilisateur, sans VPS**. L'installeur par
plateforme (sh/bat) provisionne l'hôte, télécharge les dépendances,
génère le `docker-compose.yml`, seede la base Moodle et les volumes, et
génère `opencode.json` exposant les tâches Gradle de l'écosystème
(D-ACADEMY-2).

La session S-003 a livré le **socle générateur d'installateurs**
(ACADEMY-1, 0/0/0 split) : extension typée `academyInstaller`
(Property-based), domaine pur `education.cccp.academy.installer`
(`TargetOs`, `InstallerPlatform`, `InstallerFile`,
`InstallerScriptGenerator`), tâches `generateLinuxInstaller` /
`generateWindowsInstaller` / `generateMacInstaller` /
`buildAllInstallers` (thin-wrapper `GenerateInstallerTask`), coverage
unitaire + functional TestKit + Cucumber BDD (`academy_installer.feature`,
runner S-082). Ce cadrage tranche la **forme définitive** des scripts et
l'articulation avec les Épics voisins.

== Constats (audit S-003, état réel du code)

. *Le socle ACADEMY-1 livre un scaffold* : scripts 100% déterministes
   (rendu pur, zéro I/O), pins Java/Gradle inlinés, bootstrap Docker (check
   shell Linux / cask Homebrew macOS / admin + PowerShell Windows),
   garde d'idempotence (`~/.academy/.installed-<version>`), préfixe de
   credentials via environnement (`ENV_PREFIX`) sans jamais embarquer de
   valeur, scaffold compose (Moodle + PostgreSQL + Ollama + Portainer +
   workspace opencode zsh) en heredoc uniquement quand `composeEnabled=true`.
. *Le canonical du socle est volontairement naïf* ($ sous `~/.academy`,
   Temurin/Linux via curl+tar x64, Windows via adoptium API + `setx`,
   macOS via Homebrew) — il satisfait les 7 tests de la feature mais doit
   être raffermi par plateforme (ACADEMY-6-1/2/3) : architecture multiple,
   Java/Gradle alternatives/PATH persistants côté hôte, profiles Windows,
   absence de `sudo` côté macOS.
. *Le `${ENV_PREFIX}*` n'est pas encore lu par un job* : le scaffold
   documente la convention, aucun service compose ne consomme une variable.
   ACADEMY-6-4 doit matérialiser le `.env` et sa documentation.
. *Le compose scaffold est un squelette* : services nommés, ports, volumes,
   healthchecks, réseau et seed DB **absents** (ACADEMY-6-4/6-5).
. *Aucune articulation avec ACADEMY-5 (opencode.json)* : le `run.sh` /
   `opencode.json` de la machine n'est pas généré. Le dogfooding
   (ACADEMY-6-6) exigera l'installeur + opencode + premier `gradle build`.
. *Frontière KINSHASA* : le plugin academy **ne provisionne pas** de
   runtime LLM distant (pas de Playwright/Colab/ports rotation) — il
   *distribue* une machine locale ; KINSHASA (N0) reste le provisionnement
   dev cross-borough. Aucune dépendance compile à ajouter.

== Constats du dogfooding (S-007, ACADEMY-6-6)

Le dogfooding réel (build de l'installeur Linux, extraction des heredocs,
`docker compose up` sur conteneur éphémère) a **prouvé l'enchaînement**
Docker → PostgreSQL healthy → seed one-shot (`INSERT 0 1`, puis `INSERT 0 0`
en re-run) → Moodle up (`/login/index.php` HTTP 200) — **et révélé que le
scaffold tel que livré était inexécutable** :

. *`moodle:4.5` n'existe pas* : `docker compose pull moodle` échoue
   (`pull access denied for moodle, repository does not exist`). C'était un
   placeholder jamais vérifié ; aucune image Docker officielle ne porte
   l'organisation `moodle`. Le scaffold était **non exécutable**.
. *Contrat d'environnement faux* : le scaffold émettait
   `MOODLE_DATABASE_TYPE`/`MOODLE_DATABASE_HOST`/`MOODLE_DATABASE_NAME`/
   `MOODLE_DATABASE_PASSWORD` — aucune image réelle n'expose ce contrat.
   L'image retenue attend `DB_TYPE`/`DB_HOST`/`DB_NAME`/`DB_USER`/`DB_PASS`
   + `MOODLE_USERNAME`/`MOODLE_PASSWORD`/`MOODLE_SITENAME` (auto-install).
. *Version périmée* : le scaffold visait 4.5 ; la dernière release Moodle
   est **5.2.3** (`download.moodle.org/releases/latest`) — PHP 8.3 +
   PostgreSQL 16.
. *`portainer/portainer` obsolète* : l'image maintenue est
   `portainer/portainer-ce`.
. *Healthcheck Portainer invalide* : `portainer-ce` est *distroless* (ni
   `sh`, ni `wget`) — le `test: ["CMD", "wget", ...]` échoue en boucle
   (`unhealthy`) alors que Portainer sert HTTP 200. Sonde à retirer
   (D-ACADEMY-6-17).
. *`cccp-education/academy-workspace:latest` inexistante* : le service
   `workspace` (D-ACADEMY-6-10) ferait échouer `compose up` ; différé.

Preuve du run réel (stack reconstruit sur images réelles) :
`docker compose config` VALIDE ; PostgreSQL healthy ; seed `INSERT 0 1` puis
`INSERT 0 0` (count = 1) ; Moodle **5.2.3 (Build: 20260914)** `healthy` ;
`curl /login/index.php` = **200**.

== Constat d'audit (S-008, ACADEMY-6-7)

L'audit du « contenu OS » demandé par ACADEMY-6-7 a révélé une **contradiction
gouvernance/code** : D-ACADEMY-6-10 (révision pilote S-004) tranche « l'hôte ne
provisionne **rien d'autre que Docker** — Java/Gradle vivent dans l'image
workspace », mais `InstallerScriptGenerator` émettait toujours le provisioning
hôte Java Temurin + Gradle (code S-003 jamais retiré) :

. Linux : blocs `mkdir $INSTALL_ROOT/jdk` + curl `github.com/adoptium/temurin…`
   + `tar` + `export JAVA_HOME`, puis bloc Gradle curl `services.gradle.org` +
`unzip`.
. Windows : downloads `api.adoptium.net` + `services.gradle.org` + `setx
   JAVA_HOME` / `setx PATH`.
. macOS : `brew install "openjdk@$JAVA_VERSION"` + `export JAVA_HOME` +
   `brew install gradle`.

Les tests verrouillaient ce comportement caduc (assertions S-003), ce qui
masquait l'écart. Décision de session (D-ACADEMY-6-18) : **appliquer D-6-10**
et **absorber ACADEMY-6-1/2/3** (raffermissement hôte) qui perdent tout objet —
rien n'est installé sur l'hôte hormis Docker. Le BDD est étendu pour couvrir
le contenu OS réel (hôte Docker-only, chemins de staging, marqueur versionné,
erreurs, `opencode.json` différé).

- *Preuve* : `sh -n` VALIDE (linux/macos), `docker compose config` VALIDE,
  grep `JAVA_HOME|temurin|adoptium|services.gradle.org|setx` sur les 3 scripts
  générés = **0 occurrence**.

== Options écartées

- **Ressource pré-générée binaire/zip au repo** : contredit D-ACADEMY-2 (la
  ressource est *générée* par le plugin à chaque build) et la Loi de
  l'Économie d'Encre (artefacts volatils). Écartée.
- **Atlas/Ansible/Puppet pour le provisionnement hôte** : sur-dimensionné
  pour une machine mono-utilisateur, ajoute une dépendance runtime.
  Écarté (le shell natif suffit).
- **Installeur unique multi-OS (un script bash universel + branches)** :
  le `.bat` Windows reste structurellement distinct (admin, PowerShell,
  `setx`) ; un hybride unique alourdit la maintenance et les tests.
  Écarté (D-ACADEMY-6-1 : un rendu par `TargetOs`).
- **Répliquer le provisionnement KINSHASA (Playwright/Colab/ports)** :
  hors mission — D-ACADEMY-3 tranche : academy distribue, KINSHASA provisionne le dev cross-borough. Écarté.
- **Persister les credentials dans opencode.json/`.env`** : interdit (zéro
  secret, D-ACADEMY-4 + règle Secrets gouvernance). Le `.env` de
  ACADEMY-6-5 contient seulement des noms/URLs, valeurs attendues à
  l'exécution.
