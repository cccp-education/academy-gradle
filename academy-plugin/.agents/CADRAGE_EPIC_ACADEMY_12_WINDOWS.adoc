== Contexte

Les EPICs ACADEMY-6/5/7/8/4/11 ont livré la machine d'expérimentation et
l'injection du matériel. L'installeur généré suppose toutefois que Docker est
**déjà présent** sur l'hôte : `InstallerScriptGenerator.windowsScript` se
contente de *vérifier* Docker Desktop (`InstallerScriptGenerator.kt:143`) et
`linuxScript` de *vérifier* `docker` (`:61`). Aucun OS n'est réellement
**provisionné**.

Deux constats déclenchent ce cadrage :

. Le pilote veut **installer l'engine**, pas seulement le vérifier, et le
   tester sur un **environnement Windows réel** (pas un runner CI).
. Le dogfooding S-007 n'a prouvé que **Linux**. La branche Windows — écriture
   batch (`> file (`, `escapeCmd`) — **n'a jamais été exécutée** : c'est la
   classe « scaffold inexécutable » de S-007, en attente sur la seule
   plateforme non prouvée.

La proposition initiale (« runner GitHub Windows ») a été **écartée** : les
runners `windows-latest` ne fournissent que des **conteneurs Windows**
(WSL1, images `windowsservercore`/`nanoserver` en cache) — les images
Linux (Moodle, PostgreSQL, Ollama, Portainer) n'y démarrent pas. Le test
se fera donc sur un **environnement Windows réel**, sensible à son état.

== Constats (audit S-014 — faits vérifiés, jamais supposés)

. *Docker Engine natif Windows ne fait pas tourner les images Linux.*
   `docs.docker.com/engine/install/` : « This section describes how to install
   Docker Engine on **Linux**. Docker Engine is also available for Windows,
   macOS, and Linux, **through Docker Desktop**. » Le moteur natif Windows
   (`moby`) ne voit que le noyau Windows → images `windowsservercore` /
   `nanoserver`. Or Moodle (`erseco/alpine-moodle`), `postgres:16`,
   `ollama/ollama`, `portainer/portainer-ce` sont des images **Linux**.
. *« Sans WSL » sur Windows est impossible.* Docker Desktop **exige** WSL2 (ou
   Hyper-V) et **gère sa propre distro** (`docker-desktop`) ; il *cache* WSL,
   il ne le *supprime* pas. `docs.docker.com/desktop/setup/install/windows-install/` :
   « Enabling WSL 2 for the first time also requires administrator privileges,
   but this is a one-time, per-machine operation. » Le reboot éventuel n'est
   donc **pas** éliminé par Desktop.
. *L'installeur Docker Desktop est scriptable.* Mêmes docs :
   `"Docker Desktop Installer.exe" install --user --quiet --accept-license --backend=wsl-2`.
   `--user` = sans droits admin (mode per-user recommandé) ; `--accept-license`
   supprime l'acceptation interactive ; `--backend=wsl-2` fixe le backend Linux.
   Licence gratuite pour l'éducation / OSS non-commercial / <250 employés ET
   <$10M (cccP-education éligible — à documenter).
. *Docker Engine « sans Desktop » n'existe pas sur macOS.* Docker Engine dépend
   du noyau Linux ; sur macOS il faut **toujours une VM**. L'équivalent libre de
   l'intention « sans Desktop » est **Colima** (MIT) : `brew install colima docker`
   puis `colima start`, expose le CLI `docker` standard. Alternatives : Rancher
   Desktop (Apache 2.0), Podman Desktop (Apache 2.0), Docker Desktop.
5. *La portabilité vit dans le CLI, pas dans le bootstrap.* Une fois un engine
   démarré, Linux et macOS parlent le **même** `docker` + `docker compose`. Seul
   le *démarrage* de l'engine diffère (5 lignes). Un seul `install.sh` peut donc
   porter un en-tête par OS et une **queue commune** — exactement le pattern de
   source unique déjà en place (`composeBody()`).
6. *Colima tourne aussi sur Linux* (README + CI `linux-integration.yml`) : un
   bootstrap unique `colima start` serait possible, mais imposerait une VM sur
   un OS où Docker natif existe — surcoût inutile. Écarté (voir Options).
7. *D-ACADEMY-6-12 était une erreur de catégorie.* La décision actée dit
   « Portainer remplace Docker Desktop (GUI Docker) ». Or **Portainer est une
   GUI, pas un moteur** : il exige un engine en dessous. Les deux ne sont donc
   **pas** substituables — c'est l'**engine** qui se choisit, la GUI en découle.
8. *Le préalable de build est cassé sur une machine nue.*
   `settings.gradle.kts:23` fait `error("ossrhUsername not found")` : sur un
   hôte sans `~/.gradle/gradle.properties`, **tout `./gradlew` échoue à la
   configuration** (prouvé : `./gradlew help -Duser.home=/tmp/faux` →
   `BUILD FAILED … ossrhUsername not found`). Or c'est précisément l'état d'un
   environnement Windows neuf. Vérifié : **les 25 boroughs** partagent ce
   pattern — zéro n'a de garde.

== Options écartées

- **Runner GitHub `windows-latest`** : ne fournit que des conteneurs **Windows**
  (WSL1, images Windows en cache) — Moodle/PostgreSQL/Ollama/Portainer (Linux)
  ne démarrent pas. Aucune valeur de preuve pour l'installation réelle. Écartée.
- **Docker Engine natif Windows « sans WSL »** : impossible pour les images
  Linux (noyau Windows). Contredit la matrice. Écartée (constat 1).
- **« Docker Engine sans Desktop » sur macOS** : impossible (Engine = noyau
  Linux, VM obligatoire). Remplacé par Colima. Écartée (constat 4).
- **Colima partout (Linux inclus)** : possible techniquement, mais impose une VM
  sur un OS où Docker natif existe — surcoût, redondance. Écartée (constat 6).
- **Retirer Portainer** (Desktop a déjà une GUI) : perd l'uniformité
  multiplateforme de l'expérience apprenant (même URL `:9000`, même doc).
  Gardé partout (D-ACADEMY-12-1).
- **Promettre un run Windows sans reboot** : l'activation WSL2 exige un reboot
  possible. Promettre l'inverse reproduirait la classe « scaffold inexécutable »
  (S-007). Assumé idempotent/resumable (D-ACADEMY-12-4).
