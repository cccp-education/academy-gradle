== Contexte

ACADEMY-5/7 ont livré l'**exposition** de l'agent : `opencode.json`
multi-provider (BYOK) + `AGENTS.md` + service `workspace` en profile `agent`.
Il manque le **transport** : comment un événement de formation (Moodle) ou un
tour d'agent entre/sort de la machine d'expérimentation.

`VISION_PIPELINE_FORMATION.adoc` § 8 D4 pose la question (FastAPI ou Ktor) et
recommande **Ktor** — au motif que `AGENTS.adoc` interdit Python et que « le
bridge opencode existe déjà (`SessionProtocol` de codebase) ». **Décision
pilote 2026-09-21 : Ktor est acté.** Ce cadrage en tire les conséquences
techniques réelles, vérifiées.

== Constats (audit S-011 — faits vérifiés, jamais supposés)

. *Le « bridge opencode » existant n'est PAS HTTP.* `SessionProtocolDaemonTask`
   (`codebase/koog/SessionProtocolDaemonTask.kt`) est un daemon
   **stdin/stdout JSON-lines** : `SessionProtocolServer.run(System.in,
   System.out)`, une `SessionPrompt` JSON par ligne entrante, une
   `SessionResponse` par ligne sortante. Zéro socket, zéro serveur HTTP. La
   justification de D4 (« le bridge existe déjà ») est donc **inexacte** :
   Ktor n'est pas un remplacement, c'est un **transport additionnel**. Ce
   cadrage l'assume explicitement (décision D-ACADEMY-8-1).
. *Moodle n'a pas de webhook natif.* Vérifié S-011 : le cœur Moodle expose des
   *web services* (REST/SOAP) que l'on **appelle**, mais aucun mécanisme
   d'événement sortant. Un webhook Moodle exige un **plugin tiers** — le plus
   connu étant `local_webhooks` (non vérifiable en détail : moodle.org renvoie
   un challenge Cloudflare, aucune source primaire consultable S-011). L'image
   `erseco/alpine-moodle:v5.2.3` **ne l'embarque pas**.
   → **Décision** : academy ne dépend d'aucun plugin tiers pour son contrat.
   Elle définit son **propre** schéma d'événement entrant (`MoodleEvent`),
   que n'importe quel producteur (plugin Moodle, script, curl, test) peut
   poster. Le nom `MoodleEvent` est un **vocabulaire métier**, pas une
   affirmation sur un format Moodle officiel.
. *Ktor 3.2.0 est disponible et aligné* (Maven Central vérifié S-011) :
   `ktor-server-core`, `ktor-server-netty`, `ktor-server-content-negotiation`,
   `ktor-serialization-kotlinx-json`, `ktor-server-test-host` — tous 3.2.0.
   Le `ktor-server-test-host` permet de tester le serveur **sans port réel**
   (`testApplication`), donc sans flake réseau (pattern testcontainers/TestKit).
. *Le précédent « daemon local lancé par une tâche Gradle » existe* :
   `SessionProtocolDaemonTask` (codebase, `group = "generate"`, stdin/stdout,
   `@DisableCachingByDefault`). Un serveur HTTP local lancé par une tâche
   Gradle est cohérent avec ce pattern — et avec la doctrine « aucun VPS,
   artefact de build mono-utilisateur » (`AGENT.adoc`, vision § 3.3) : on
   reste **local**, jamais hébergé.
. *Les contrats N0 nécessaires existent et sont publiés* :
   `contracts.session.{SessionPrompt, SessionResponse, SessionStatus,
   ToolCallRecord, AgentContext, TokenUsage}` (`opencode-session-contracts:0.0.2`,
   Central) — déjà transitif via `runtime-contracts` (déclaré ACADEMY-7).
. *Le plugin n'a aucune dépendance de sérialisation* : `opencode.json` est
   rendu par concaténation littérale (D-ACADEMY-5-3/7-4). Recevoir du JSON
   HTTP **exige** une vraie sérialisation — c'est un changement de nature,
   assumé ici (D-ACADEMY-8-3).
. *Le coût Ktor est réel et mesurable* : ~5 artefacts + Netty pèsent sur le
   classpath de **tout consommateur** du plugin. Mesuré S-011 comme un
   trade-off conscient, pas un effet de bord (D-ACADEMY-8-2).

| D-ACADEMY-8-3 | **Sérialisation kotlinx** (`kotlinx-serialization-json` via `ktor-serialization-kotlinx-json`) : recevoir du JSON HTTP exige une vraie sérialisation (le rendu par concaténation de D-ACADEMY-5-3 ne s'applique pas à l'entrée). == Schéma d'événement entrant (contrat academy — D-ACADEMY-8-5)

```
POST /events/moodle
{
  "eventName": "course_module_completed",   // vocabulaire academy, jamais revendiqué Moodle
  "courseId":  "academy-seed",
  "userId":    "learner-1",
  "payload":   { "module": "M01" }          // libre, opaque pour le bridge
}
```

Traduction (domaine pur `BridgeEventTranslator`) → `SessionPrompt` N0 :
`prompt` = phrase déterministe dérivée de `eventName` + `courseId` + `userId`,
`context` = `payload` sérialisé en clé/valeur, `sessionId` dérivé de manière
stable (pas d'aléatoire : le bridge est rejouable/testable).

== Options écartées

- **Réutiliser tel quel `SessionProtocolDaemonTask` en stdin/stdout** : ne
  répond pas au besoin « un producteur externe pousse un événement » (pas de
  socket), et c'est un artefact **N1 codebase** — academy ne peut pas en
  dépendre (DAG N2 : jamais N2 → N1 par import de tâche). Écartée
  (D-ACADEMY-8-1).
- **Dépendre du format `local_webhooks`** : plugin tiers absent de l'image,
  payload non vérifiable S-011 (Cloudflare). Figer un format non documenté
  reproduit la classe de bug `moodle:4.5` (S-007). Écartée (D-ACADEMY-8-5).
- **Générer un projet Ktor complet dans le scaffold** : duplique du code non
  testé, dérive de version, et sort du périmètre « exposition » d'academy.
  Écartée.
- **Exécuter l'agent (LLM) dans le bridge** : contredit la boundary
  (« consommateur terminal, n'injecte aucun LLM de génération ») ; l'agent
  reste opencode, le bridge route. Écartée (D-ACADEMY-8-6).
- **Démarrer le serveur par défaut** (`bridgeEnabled = true`) : un plugin de
  build ne doit pas ouvrir un port sans opt-in explicite. Écartée
  (D-ACADEMY-8-7).
- **Tests HTTP par port réel partout** : flaky et lent ; `testApplication` pour
  les tests, port réel **uniquement** pour le dogfooding (preuve). Écartée
  (D-ACADEMY-8-10).
