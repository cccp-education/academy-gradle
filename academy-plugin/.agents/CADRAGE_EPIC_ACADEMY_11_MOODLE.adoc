== Contexte

`PROMPT_REPRISE` S-012 propose deux candidats : ACADEMY-2/3
(`FormationRuntimePort`/`SessionMemoryContract`) et ACADEMY-10 (migration
Spring Boot). L'arbitrage pilote du 2026-09-21 **recadre** la mission :

[quote]
____
« academy aide à **consommer la formation** qui est générée par training et
**installe le runtime nécessaire au travers de Docker** pour le client qui
achète l'archive de la formation. »
____

[quote]
____
« Je n'injecte pas de l'implémentation mais j'injecte de la **data
structurée** pour être consommée en AsciiDoc et **intégrée dans Moodle**. »
____

Le trou visé n'est donc **pas** la boucle agentique (ACADEMY-2/3) mais la
**US différée `ACADEMY-4-2*`** (« alimenter le cours Moodle seedé depuis le
matériel reçu »), que D-ACADEMY-4-12 avait reportée faute de contrat SPG/SPD
canonique. Le runtime Docker (ACADEMY-6) et l'exposition agent (ACADEMY-5/7)
sont déjà livrés ; il manque le **contenu**.

== Constats (audit S-013 — faits vérifiés, jamais supposés)

. *La frontière de `FormationRuntimePort` est tranchée — et elle exclut
   academy.* Trois sources convergent : `VISION_FORMATION_INTERACTIVE.adoc`
   § D3 + itération 9 (« Split — academy = infra OSS, **edster/workspace-gradle
   = runtime agentique privé**, LocalAdapter + CloudAdapter »), la KDoc de
   `bureau/BureauPlugin.kt:24` (« The private edition (workspace-gradle)
   implements FormationRuntimePort for edster.cloud ») et la règle licence
   3 étages (`AGENTS.adoc` : « orchestration agentique = privé, la marge »).
   `VISION_PIPELINE_FORMATION.adoc` § 6 (« academy est l'implémenteur de ces
   contrats ») est **contredit** par ces trois sources, toutes postérieures ou
   plus précises. L'arbitrage pilote S-013 tranche : **academy n'implémente
   pas la boucle runtime**.
. *`SessionMemoryContract` a DÉJÀ un implémenteur — le TODO est périmé.*
   `grep` cross-borough : `codex-plugin/src/main/kotlin/codex/profile/PgVectorSessionMemory.kt:37`
   implémente le contrat N0 depuis S-094 (EPIC CDX-RC-04), avec persistance
   pgvector, embedding ONNX `AllMiniLmL6V2` et la tâche `persistLearnerProfile`.
   Le VISION § 6 (« zéro implémenteur ») était vrai à l'écriture ; il ne l'est
   plus. Le seul contrat réellement dormant côté runtime est
   `FormationRuntimePort`.
. *`ToolExposure` (N0) est un contrat orphelin — academy est son
   consommateur désigné.* Le JAR `runtime-contracts:0.0.1` publié (inspecté
   S-013 : `contracts/runtime/ToolExposure.class`) contient le contrat ; son
   unique mention dans le code prod academy est une KDoc (`OpenCodePlugin.kt:9`).
   Le guardrail `foundry/public` est aujourd'hui porté par un **commentaire**,
   pas par le contrat (TODO S-012).
. *Moodle expose des mécanismes d'ingestion officiels — rien à inventer.*
   Audit de l'image réelle `erseco/alpine-moodle:v5.2.3` (Moodle **5.2.3**,
   racine `/usr/src/moodle`, web `/var/www/html`) :
   +
   [cols="2,3,2", options="header"]
   |===
   | Mécanisme | Chemin réel vérifié | Usage
   | `create_course()` | `public/course/lib.php:1768` | API officielle de création de cours
   | `add_moduleinfo()` | `public/course/modlib.php:49` | API officielle d'ajout d'activité à une section
   | `course_create_sections_if_missing()` | `public/course/lib.php:550` | API officielle de création de section
   | `restore_backup.php` | `admin/cli/restore_backup.php` (`--file=X.mbz --categoryid=N`) | restauration d'une sauvegarde `.mbz`
   | `import.php` | `admin/cli/import.php` | import **inter-cours** (source→dest), pas depuis un fichier externe
   | `uploadcourse.php` | `public/admin/tool/uploadcourse/cli/uploadcourse.php` (`--file=X.csv`) | métadonnées de cours uniquement (pas de contenu)
   |===
   +
   Modules de contenu disponibles : `page`, `label`, `book`, `quiz`, `folder`,
   `resource`, `subsection`, `url`.
. *L'IMAGE EMBARQUE DES OUTILS NATIFS — on ne construit pas de stack.*
   Découverte décisive S-013 (audit image réelle, arbitrage pilote
   « on s'appuie sur l'image préconstruite et ses outils natifs »). L'image
   `erseco/alpine-moodle:v5.2.3` **préconstruit** deux outils de provisionnement :
   +
   [cols="2,4,2", options="header"]
   |===
   | Outil | Chemin réel vérifié | Capacité
   | `moodle-blueprint` | `/usr/local/bin/moodle-blueprint` (+ lib `/usr/local/lib/moodle-blueprint/`) | applique un `blueprint.json` **format Moodle Playground**, **automatiquement au démarrage** du conteneur via `MOODLE_BLUEPRINT` (hook `docker-entrypoint-init.d/03-apply-blueprint.sh`). Étapes **implémentées** (vérifiées `StepRegistry.php`) : `createCategory`, `createCourse`, `createUser`, `createUsers`, `enrolUser`, `setConfig`, `installMoodlePlugin`, `installTheme`, `setTheme`. Idempotent par `canonicalHash` + marqueur `.done`.
   | `moosh` | `/usr/local/bin/moosh` (+ `/opt/moosh/`) | Moodle Shell complet (CLI natif) : `course-create` (`-f fullname -F format -r reuse` — **idempotent**), `activity-add` (`-n name -s section <type> <course>`), `section-config-set`, `label-create`, `course-restore`, `category-create`.
   |===
   +
   *Conséquence de conception* : academy n'a **pas** à réimplémenter l'API
   Moodle dans un script PHP maison (ce serait bâtir une stack). Il génère la
   **donnée** (le plan) et un applicateur **générique** qui **pilote les outils
   natifs de l'image**.
   +
   _Limite vérifiée_ : `moodle-blueprint` classe `createSection` et `addModule`
   en **PLANNED** (reconnues mais non implémentées → échec clair). Le cours se
   crée nativement par blueprint, mais **sections et activités passent par
   `moosh`** (qui, lui, les implémente).
. *Le format `.mbz` est un binaire opaque — le fabriquer à la main est un
   piège.* Aucun `.mbz` ne se génère par concaténation : c'est une archive de
   sauvegarde Moodle (`backup/moodle2`) dont la structure dépend de la version.
   Un `.mbz` forgé reproduirait la classe de bug « scaffold inexécutable »
   (S-007 `moodle:4.5`, S-012 `hasRequirement()`). Le mécanisme robuste est
   l'**outil natif de l'image** (`moodle-blueprint` + `moosh`), ou la
   restauration d'un `.mbz` **réel** fourni par le producteur.
. *Le seed existant crée une coquille, pas du contenu.* ACADEMY-6-5 seede
   `mdl_course` (`INSERT ... WHERE NOT EXISTS` sur `idnumber='academy-seed'`,
   service one-shot `moodle-seed`, entrypoint idempotent). Il ne crée ni
   section, ni activité — c'est précisément ce qu'ACADEMY-11 ajoute.
. *La structure du matériel est portée par le filesystem (convention over
   configuration).* `training` infère les métadonnées par convention
   (`FormationMetadataExtractor` : dossier = module, préfixe numérique = ordre,
   premier `= Titre` = titre) et produit `build/spg/spg.adoc` +
   `build/spd/{module}/{session}.adoc` + un `metadata.json` **pivot EPIC K**
   par artefact. Academy lit déjà ce pivot (`MaterialManifest.fromJson`,
   S-012) — il le **réutilise** pour l'ingestion.
. *Le boundary § 3.3 interdit à academy de parser le contenu AsciiDoc.*
   « academy est un consommateur terminal. Il ne génère rien, n'injecte aucun
   LLM de génération, **ne parse pas les `.adoc` sources**. Il présente et
   assiste. » L'ingestion doit donc traiter les fichiers AsciiDoc comme un
   **payload opaque** (transportés, jamais interprétés) et ne lire que la
   **structure** (arborescence + pivots).
. *Le matériel réel est encore rare* — `office/trainings/FPA_CDA/.../prepro-cda_SPG.adoc`
   = 5 lignes ; `office/metiers/FPA/cours/` porte 19 modules d'AsciiDoc réels
   mais hors convention training. Le dogfooding devra donc utiliser une
   **fixture conforme** (pattern S-012), et le matériel FPA réel servira de
   test d'intégration ultérieur.

== Le mécanisme d'ingestion (fait vérifié — D-ACADEMY-11-2)

```
materialDir/                              (transporté par le bureau, BUREAU-3)
├── SPG/metadata.json + spg.adoc          (artefact SPG, pivot EPIC K)
├── SPD/01_module/001_seance.adoc         (convention : dossier=module, fichier=séance)
│   └── metadata.json
└── QUIZ/metadata.json + quiz.adoc

        │  MoodlePlanBuilder (PUR — lit la structure + les pivots)
        ▼
build/academy/moodle/plan.json            (DATA STRUCTURÉE — le contrat stable)
build/academy/moodle/ingest.sh            (applicateur GÉNÉRIQUE — pilote les outils natifs)

        │  service one-shot `moodle-material` (compose, après le schéma Moodle)
        ▼
sh /ingest/ingest.sh
   ├─ moodle-blueprint  (blueprint.json)  → crée le cours (idempotent)
   └─ moosh course-create -f ... -r        → crée/réutilise le cours
      moosh section-config-set …           → nomme chaque section (module)
      moosh activity-add <type> … -s <n>   → injecte chaque activité
```

*Idempotence* : `moodle-blueprint` marque `.done` par `canonicalHash`,
`moosh course-create -r` réutilise un cours existant — rejouer ne duplique rien.

== Options écartées

- **Implémenter `FormationRuntimePort` dans academy** (VISION_PIPELINE § 6 lu
  au pied de la lettre) : déplace la frontière licence et duplique l'étage
  « orchestration agentique = marge privée ». Écartée (D-ACADEMY-11-1,
  arbitrage pilote S-013).
- **Forger un `.mbz` par concaténation** : archive binaire version-dépendante,
  non fabricable de façon fiable ; reproduirait S-007. Écartée (D-ACADEMY-11-2).
- **Injecter par SQL direct** (`mdl_page`, `mdl_course_sections`) : couplage
  fort au schéma interne Moodle, silencieusement cassé à chaque upgrade.
  Écartée — l'API officielle est stable, le SQL ne l'est pas.
- **Parser le contenu AsciiDoc dans academy** : viole le boundary § 3.3 et
  dupliquerait le travail de document/codex. Écartée (D-ACADEMY-11-4).
- **Fusionner ACADEMY-9 (Qualiopi) dans ACADEMY-11** : périmètres distincts
  (contenu vs traces). Écartée (D-ACADEMY-11-10).
- **Exiger le contrat SPG/SPD canonique avant de coder** (raison de la
  défération S-012) : l'ingestion lit la **structure par convention** déjà
  implémentée par training (`FormationMetadataExtractor`) et le **pivot EPIC K**
  déjà lu par academy — elle n'exige pas le contrat sémantique. Le dogfooding
  utilisera une fixture conforme. Écartée.
